# Project rules

- Keep the real-account Personal Profile release candidate in a separate preview-only route and owner-scoped social tables; do not reuse account settings or demo fixtures, and visitor access is released only by the server env flag PERSONAL_PROFILE_VISITORS_RELEASED (owner-approved Nov 2026).

- Share identity-log search validation and shortcut helpers between the audit and detail pages so return navigation preserves the same fingerprint, acting-user, and time filters.
- Admin's parent route always renders Outlet and renders the dashboard only for its exact match so admin tools can display their own screens.
- Use optional search schemas for optional navigation filters so existing links need no invented search values.
- Store single-use passkey challenges in a service-only database table bound to origin, purpose, expiry, and registration owner; workers do not share memory.
- Return web OAuth to the public origin and preserve the sanitized destination separately until the auth server validates the session.
- Keep app email sends in their feature server handlers through the managed template helper; retained email tables are notification history, never send gates.
- Deduplicate terminal email history by a deterministic event ID so signed webhook retries remain safe without changing retained table schemas.
- Managed Stripe notifications use /api/public/payments/webhook with signed environment selection; sandbox notifications never mutate shared production orders.
- Checkout verification uses admin-gated embedded sandbox sessions and server-verified account ownership on the return page; never infer payment success from URL flags.
- Marketplace checkout uses embedded gateway sessions with explicit environment selection and database-derived totals; sandbox sessions omit seller transfers and never stamp production order payment fields.
- Preview must reject seller withdrawal requests and live Connect account changes before side effects; all signed Stripe event processors ignore non-live events because preview shares production balances.
- Marketplace payment regression checks run real sandbox Embedded Checkout through the cart, verify Stripe intents/charges and signed notifications, and clean up only their own unpaid fixtures.
- Target Model A uses Separate Charges and Transfers with environment-scoped seller accounting; keep the existing production charge model until an explicitly approved cutover, because legacy destination charges must never be transferred again.
- Keep unapproved financial release candidates and tests outside application imports and migration directories so review preparation cannot alter production behavior.
- Expose guest auction queues only through the read-only public projection RPC; preserve base-table policies so seller and transaction details remain protected.
- Keep marketplace departments separate from legacy collectible category keys and store general attributes on shared listings; this preserves scanner/Vault compatibility and existing orders.
- Public marketplace search uses a bounded safe-column projection shared by Marketplace, Discover and category shopping; this prevents seller-profile leakage and divergent publication rules.
- Dedicated department shopping URLs use shared configuration and public projection reads, not separate inventories; category keys and collectible subcategories remain distinct.
- Router factories own the per-request QueryClient and SSR query hydration, and the root uses that client; this keeps loader priming and component subscriptions consistent without cross-user caches.
- PB Bazaar uses its own store/product/variant tables with database-enforced store review; never reuse Marketplace listings or PB Store products, so retail inventory and permissions stay isolated.
- Bazaar shopping detail/cart reads use an anonymous safe-column server projection regardless of staff sessions; browser-local cart stores only identifiers, quantities and last-seen prices, so private catalogs and existing payment records stay isolated until account/order schema approval.
- Keep Bazaar account/order/supplier design candidates outside application imports and migration directories until separately authorized; guest imports are idempotent, private data uses scoped projections, and inventory/order transitions require environment-scoped database transactions to prevent cross-store leakage and overselling.
- Bazaar supplier data (suppliers, costs, links, pricing, sync history) is admin-only; shoppers get variant availability and delivery windows solely through the bazaar_public_variant_availability projection, and demo or unapproved supplier products are blocked from publishing by trigger.
- Category presentation reuses shared department keys and bundled optimized photography; interest personalization uses existing owner-scoped profile interests with legacy collectible preferences preserved, so navigation and inventories stay compatible without new account schema.
- Public stabilization uses shared pure detail/activity/intent helpers and request-version guards for Marketplace reads; unavailable data must never be presented as zero activity or stale results from another filter.
- Listing detail refreshes preserve the mounted page until the newest read completes; only listing/viewer changes reset loading, so realtime activity does not interrupt forms or dialogs.
- The preview administration portal reuses existing protected owner/admin roles and caller-scoped server reads, keeps legacy tool URLs intact, and scopes branding/favicon locally; new memberships, permission groups and email events require separate authorization.
- Personal Profile redesign activates only in local development or recognized hosted/embedded Lovable previews after hydration, without mounting the legacy account panel while classification is pending; signed-out design shells expose no account data, owner reads and drafts stay scoped, and visitor social reads remain disabled until privacy approval because preview shares production data.
- Vault privacy review controls use owner-scoped read-only card projections and in-memory audience/show selections on preview-only routes; persistence and show authorization remain isolated release candidates so preview cannot change shared privacy.
- Personal Profile Stage 1 uses session-only demo fixtures and bundled media for all interactions, clears open content on viewer changes, and keeps account management separate; this permits functional review without touching customer data or treating client simulation as server security.
- Personal Profile visitors read only through the server projection and /api/personal-media authorization, which re-derive tier (owner/close friend/follower/member/guest/blocked both ways) per request; base tables keep owner-only RLS and without the release flag both paths refuse non-isolated backends and released domains; accounts without a social identity fall back to public profile basics plus approved public feed posts.
- Personal profiles live at /@username (prefix route); owner status comes only from the verified session, with a safe fallback to the account username/name until the owner first saves, so a missing social identity row never locks the owner out.
- Seller storefront tabs are commerce-only (Shop, Live Shows, Reviews, Sold, About); social posts and Vault cards live on the personal profile/Vault, and owner controls hide in Preview as Buyer.
- Phone navigation uses a constrained search grid with named icon shortcuts, and storefront controls wrap independently from identity text; this prevents narrow-screen clipping without changing menu destinations.
- Vehicle listings save only a masked VIN in public product details; full VINs need a private, consent-gated store because listing details are publicly readable.
- PB Bazaar supplier integrations implement the SupplierAdapter contract in src/lib/suppliers as server-only modules; CJ order creation stays opt-in via env and balance payment is manual-only, so no supplier spend happens automatically.
- PB Store and PB Bazaar are fixed-price only (cart, Buy Now, checkout); listings.channel plus DB constraint/triggers reject auctions, bids and offers for those divisions, while Marketplace and live auctions stay unchanged.
- PB Bazaar orders live in dedicated bazaar_order* tables (sandbox/USD only); browsers only read their own orders, and all writes, stock holds and payment settlement go through service-only database functions so payment and inventory change together in one place.
- PB Bazaar Buy Now and cart checkout share one server engine (bazaarCheckout.server.ts) that rechecks live CJ cost/stock/shipping and Stripe Tax before holding stock; the signed sandbox webhook alone settles payment, so browsers and return URLs never mark orders paid.
- Bazaar catalog management paginates products on the authenticated server, loads complete variant groups per page and limits bulk actions to hidden drafts; this avoids catalog caps and partial-variant publication.
- CJ catalog scanning runs only in the hosted scheduled worker under a database lease with checkpoints and one outcome row per CJ product; fast imports stay unverified/inactive until the per-product CJ recheck, so the browser never drives or races the scan and counts reconcile.
- Public Bazaar catalog also lists genuine (non-demo) supplier drafts in active stores via a server safe-column projection with no prices or variants, labeled Coming soon; checkout still requires published products with verified options.
- CJ Stage 2 qualification runs inside the hosted scan tick: only options with live stock, a confirmed US shipping quote and the profit floor are approved/activated, failures are rejected with a recorded reason, and a product auto-publishes with >= 1 passing option; visibility still depends on the store being active, so launch stays a separate decision.
- Flex mature rooms use the MATURE_TAG value in tcg_tags (no schema change); avatars show to all non-blocked viewers (owner-approved).
- Profile look (store logo, cover position, layout) is owner-edited profiles columns read by visitors via server projections.
