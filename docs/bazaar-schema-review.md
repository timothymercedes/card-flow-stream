# PB Bazaar — revised schema and execution review

**Revision:** 2026-11-13. **Status: design refinement only; NOT approved for database execution.**

This document replaces the short schema proposal in `bazaar-roadmap.md`. It defines a proposed contract, not deployed tables or verified future behavior. No application code, database schema/data, access policies, supplier connection, payment configuration or deployment is changed by this review.

## 1. Boundaries and evidence

- Preserve current product pages, anonymous safe-column shopping reads, browser-persistent multi-store cart, store approval, team roles and private-media rules. Preserve Marketplace, PB Store and all auction/payment/payout behavior. No automatic inventory copying between businesses.
- Account carts, order creation, reservations and supplier processing remain disconnected from application imports until separately authorized. Checkout remains disabled. Payment/refund references below describe future accounting only; they do not activate payments or refunds.
- Basis: repository foundation migrations `0008`–`0011`, shopping projection, cart helpers/hook, and previous evidence-labeled test report. No fresh hosted-schema drift inspection, supplier API verification, populated signed-in shopping or proposed-schema execution was performed for this revision.
- Preview currently shares the live database. A preview label, test flag or test payment mode does **not** isolate database writes. Do not execute tests, create fixtures or apply migrations there under this approval.
- Proposed defaults (not settled business policies): reservation lifetime 15 minutes; supplier acceptance deadline 24 hours, subject to each verified supplier contract; no automatic substitutions; signed-in order creation only. Confirm these defaults before implementing them. Return windows, shipping refundability, taxes and supplier service levels remain release gates.

## 2. Guest and account carts

**Guest:** continue the existing browser cart key and identifier/quantity/last-seen-price format. No customer identity, address, supplier cost or durable backend guest cart. Adding to any cart never reserves stock. Guests can browse/add/remove; future order creation requires sign-in. No cross-device guest transfer promised.

**Future sign-in transfer:** after the server verifies a session, offer a merge of this browser's guest cart into that customer's account cart. Do not infer ownership from an email, URL or browser-supplied customer ID. Declining or failed sign-in keeps the guest cart unchanged.

1. Send a bounded, validated snapshot plus a persisted random import key. Match existing parser limits (100 distinct variants, positive integer quantities up to 10,000); additionally enforce current stock and any future per-item limit. Resolve product/store/variant identity server-side.
2. Lock the account cart; require expected revision for normal edits. Merge identical variants by summing once per import, clamp only with an explicit stock-reduction result; unavailable lines stay in a browser-only review list, not hidden catalog snapshots. Changed prices require acknowledgment before future order creation.
3. Transactionally insert an import receipt with payload hash. Retrying the same key/hash returns the original result without adding again; same key/different payload rejects. Concurrent imports use the same cart lock. Imports and account edits are never last-write-wins silent overwrites.
4. Clear only the imported snapshot after durable acknowledgment. Compare local lines to the sent version; preserve edits made during transfer and retain rejected lines for removal/review. Lost acknowledgment is safe to retry.
5. Account cache keys are user-scoped. Sign-out removes account cache/private data from the browser; it does not copy account lines into the guest cart. On a shared browser, a different account sees neither the previous account cart nor a stale merge offer. A genuine pre-sign-in guest cart remains independent.

Account carts retain unavailable identifiers/last-seen prices as non-buyable lines. Cart reads must not expose hidden product descriptions or media through privileged joins. Price/currency changes never silently reprice an accepted order.

## 3. Mandatory server validation and atomic order boundary

Future order creation accepts cart ID/revision, expected quote hash, destination input and idempotency key—not totals, customer identity, supplier routing, discounts or lifecycle status. Verify customer identity from the session; validate currency, country/address and restricted-category eligibility. Currency is server-configured: existing variant prices have **no currency column**, so currency activation/configuration must be explicitly reviewed; clients cannot label the same cents as another currency.

Before reserving or creating anything, re-read and lock every referenced store, product and variant in deterministic ID order. Validate active/approved store, published product, active variant, exact variant/product/store membership, positive quantity, fresh price, available stock, shipping eligibility and quote validity. Store/product row locks prevent approval/publication races. Return line-specific unavailable/price/stock results; no silent substitution or partial parent creation. Require confirmation of a new quote if any financial input changed.

For supplier stock, obtain a fresh authenticated supplier quote outside the database transaction; fail closed on unavailable/expired/unsupported results. A quote is **not** a supplier stock guarantee. Record quote expiry/hash and recheck local mapping/version inside the transaction. External calls cannot be atomic with PostgreSQL; supplier rejection is a compensating workflow, not evidence the local reservation was guaranteed upstream.

One transaction: lock cart → stores/products/variants (sorted) → private inventory controls → create immutable parent/store/item snapshots → reserve all lines → append initial audit events → mark cart ordered. If any line fails, roll back **all** these writes. An idempotency row is the parent unique customer/environment/key; retries with different hashes reject, completed retries return the same safe order. No external provider calls while database locks are held.

Parent stores/store orders must use one currency; subtotal, allocated discounts, tax and shipping sums must match exactly. Use integer minor units (bigint in storage, safe serialization as strings where necessary), never floating point. Currency exponent/allowed currencies are configured server-side. Immutable order snapshots survive later catalog edits/deletion.

## 4. Inventory reservation protocol

- Existing `bazaar_product_variants.quantity` remains physical/on-hand stock, not an amount decremented when a cart changes. Proposed private inventory control tracks `held_quantity`; sellable = on-hand minus holds. Lock variant/control rows for every hold, commit, release and stock edit. Holds never make sellable negative.
- Existing public shopping/media policies are preserved. A separately approved coupled inventory release must update safe availability projections **and** enforce catalog stock edits with a trigger so quantity cannot fall below active holds. Product editor roles still edit stock; they cannot edit hold counters or clear reservations. These additions are a future behavior change requiring explicit approval, not part of this document.
- Reserve sets `held` and server-calculated expiry (proposed 15 minutes). Expiry must be later than transaction time via validation trigger, not time-dependent CHECK. The timestamp, renewal and deadline cannot be supplied by customers. No indefinite client renewals.
- Expire/release is transactional and idempotent: lock order/variant/control/reservation; decrement hold exactly once; append event; move reservation to released/expired and update unpaid order status. Reclamation happens before new availability/reservation checks, plus one bounded expiry job only after scheduling approval. A missed job cannot cause overselling; it can temporarily understate public stock. No process-memory timers.
- `held → committed` converts reserved units to purchased inventory: atomically decrement on-hand and held; committed units are no longer expirable. Commit requires a future independently verified financial authorization boundary; a URL success flag or client claim cannot commit. Commit racing expiry has a single lock-protected winner; late authorization is quarantined for reconciliation, never forwarded to a supplier.
- Pre-commit cancellation releases holds. Post-commit cancellation restores locally committed stock once only when not dispatched and supplier cancellation is confirmed. A shipped return restocks only after inspected, accepted receipt; damaged/lost units are not automatically sellable. Use stock-adjustment audit events and prohibit duplicate replenishment.
- Supplier-backed availability is conservative (verified source stock minus local obligations); simultaneous upstream sales may still cause rejection. No automatic replacement supplier, variant or price.

## 5. Schema dictionary

### Shared conventions and complete relationship rules

All proposed tables below live in `public`; UUID `id` primary key default generated, `environment` text NOT NULL CHECK (`test`,`live`), `created_at` timestamptz NOT NULL default now. Mutable tables additionally have `updated_at` and integer `revision` default 0. Fields are NOT NULL unless marked `?`; empty object/array JSON defaults are explicit. State columns are text with static allowlists; transitions are trigger/RPC guarded, not arbitrary updates. User IDs are plain UUID with no `auth.users` FK; no new profile table.

Every new table has UNIQUE `(environment,id)`. Every FK between new tables carries `environment`, uses RESTRICT on delete/update, and has an explicit referencing-column btree index unless covered by a listed leading-key unique index. Other uniqueness is environment-scoped unless stated otherwise. Existing catalog/store FKs use RESTRICT; a validation trigger checks the parent relationships (no current catalog columns/unique constraints altered just to support composite FKs). User deletion is a separate redaction/retention process, not a cascading financial deletion. All scope fields are immutable after insert. No FK to Marketplace orders/listings or PB Store.

The fields listed per table, plus these common fields, are the proposed complete initial column set. No free-form supplier payload, secrets or buyer address may be added to a public/readable JSON column. Static checks enforce nonnegative money/quantities, positive purchased/requested/allocated units and bounded JSON/text; aggregate/time/state constraints use locked transactions and validation triggers. Index shorthand `U` = unique btree, `I` = ordinary btree, `P` = partial index. PK/shared environment keys are in addition to those listed below.

### Why additional tables are needed

The original 13-table sketch did not model idempotent guest imports, private per-store delivery details, hold counters, per-line partial shipments, partial adjustment accounting, durable supplier commands or order audit history. These seven additions close those gaps without reusing existing financial tables. They are design proposals, not authorization to build a financial subsystem.

## 6. Permissions, grants and RLS matrix

**No anonymous grants or policies on any proposed table.** Existing public catalog/media access stays unchanged. No browser/customer/merchant/supplier can directly INSERT, UPDATE or DELETE order, inventory, adjustment or event records. RLS is enabled on every new table; lack of a policy means denied, including admin. Service role bypasses RLS, so handler authorization and field validation are mandatory, not optional.

Policy keys: `C` = auth.uid() matches verified cart/order customer in the **current server environment**; `O` = customer ownership reached through parent; `M` = existing store owner or role admin/fulfillment for exactly this store; `A` = existing platform admin/owner in protected user_roles. Catalog/viewer roles receive no order/customer/address access. A merchant who is also a customer receives customer access only to orders they personally own.

| Tables | authenticated direct grants and SELECT policy | Authenticated write RPCs | Service-only operations / minimum table grants |
|---|---|---|---|
| carts, cart items | SELECT; C (items via cart), no M/A cart policy | customer cart create/edit/remove/merge with C, revision guard; no direct DML grants | SELECT/INSERT/UPDATE; DELETE cart items only; receipt/order linkage guarded |
| cart imports | none; receipt returned safely by owner-scoped merge RPC | merge only | SELECT/INSERT; append-only |
| customer orders | SELECT; C or A; never M via child order | request order preparation only after separate enablement | SELECT/INSERT/UPDATE guarded lifecycle; no DELETE |
| store orders, order items | SELECT; O or M or A | none | SELECT/INSERT/UPDATE guarded lifecycle; no DELETE |
| delivery details | none; customer/M/A receive purpose-limited DTO through server function | none; destination accepted as validated preparation input | SELECT/INSERT/UPDATE only for approved redaction/correction; no broad contact export |
| suppliers, supplier links | none; A via role-verified management server function; costs not merchant-visible | no direct RPC, approved admin handler only | SELECT/INSERT/UPDATE; approved mapping/import/config changes, no credentials in rows |
| inventory controls/reservations | none, including A direct | none | SELECT/INSERT/UPDATE; reserve/release/expire/commit/restock only |
| fulfillments, fulfillment items, supplier commands | none; safe O/M/A tracking DTO, excluding supplier IDs, commands, costs, private errors/external order IDs | merchant fulfillment action through authorized handler, never direct transition | SELECT/INSERT/UPDATE; allocation, leasing, provider transitions |
| shipments, shipment items | SELECT; O or M or A; contain only safe tracking/allocation fields | merchant dispatch via M handler; signed provider handler | SELECT/INSERT/UPDATE; monotone tracking/quantity checks |
| requests | SELECT; O or M or A | C creates for owned line; M reviews own store; all quantity/state checks inside transaction | SELECT/INSERT/UPDATE; no DELETE or ownership changes |
| adjustments | none; safe O amount summary, M own-store summary excluding external refs, A diagnostic via role-verified handler | none; financial execution remains disabled | SELECT/INSERT only; append reversal/outcome entries, no UPDATE/DELETE |
| supplier events | none; A sanitized diagnostic handler only; suppliers never receive Data API credentials | none | SELECT/INSERT/UPDATE processing fields; payload hash/key immutable |
| order events | none; safe O/M timeline scoped to their order portion; A audit handler | none | SELECT/INSERT only; immutable history |

For every direct-read table, named SELECT policies will be separate `bazaar_<table>_customer_read`, `_merchant_read`, `_platform_read` with the applicable predicate above. No permissive ALL policy; no anon policy; no base-table write policy. Every customer/merchant predicate includes scope/environment and requires nonnull auth.uid(). Helpers performing RLS parent checks must not recursively query their own protected table.

**Write/function permissions:** revoke EXECUTE from PUBLIC/anon by default. Grant authenticated EXECUTE only on owner-derived cart operations and request entrypoints; derive auth.uid() inside, never accept a trusted customer ID. Cart procedures use restricted SECURITY DEFINER only to enforce ownership/limits without granting direct DML. Authorize M/A with the user's RLS client before dynamic server-only privileged imports. All reserve/commit/release/adjustment/supplier/expiry procedures execute only for service_role. Trigger helpers receive no client EXECUTE grant. Pin search_path, schema-qualify relations, avoid dynamic SQL, validate tenant/environment in every procedure, and do not use caller-controlled JWT metadata for roles.

**Grant order in future migrations:** CREATE TABLE → explicit authenticated SELECT grants only where listed and minimal service-role DML grants → ENABLE RLS → create policies. Create helpers before dependent policies. Table-level grants alone do not authorize a row. No authenticated SELECT on private supplier/address/adjustment tables just because a projection exists. Definer views must not bypass RLS; prefer authenticated safe server DTOs, no exposed privileged views.

**Environment enforcement:** dedicated deployments pin environment server-side; browser flags never choose it. With physically separate test/live backends, ordinary RLS still applies. If a shared-backend alternative is separately approved, a trusted DB configuration/server operation (not client-editable session settings) must enforce environment; write-capable authenticated procedures are withheld until that boundary is demonstrated.

## 7. Supplier failures and partial lifecycle

Supplier customers/partners are external principals, not ordinary store team roles. No direct database access is proposed. A future signed provider event endpoint resolves supplier and environment from its verified credential, timestamp and replay key—not an arbitrary supplied supplier/store ID. Reject unknown signatures and quarantine unknown order references; never mutate an order from a matching display name or tracking number alone. If signature verification is unavailable, supplier ordering stays disabled until an authenticated verification alternative is reviewed.

Future outbox: commit a supplier command with fulfillment/allocation first; a bounded worker leases it, makes authorized external calls outside transactions, then records verified outcomes transactionally. Use stable provider idempotency keys. Timeout after submission becomes `acceptance_unknown`; query verified external status before any resubmit. A provider lacking idempotency/status reconciliation requires manual review, not blind retries. Do not activate workers, outbound ordering, jobs or webhooks in this phase.

| Condition | Designed response |
|---|---|
| Supplier rejects / item unavailable | Record rejected allocations and customer-visible reason code; release pre-commit holds or append once-only cancellation/financial credit after commit; no substitution or double restock |
| Mixed accepted/rejected units | Keep accepted units fulfilling; cancel only rejected units; parent/store state becomes partial; never cancel unrelated stores or duplicate the accepted order |
| Acceptance deadline missed | Mark delayed/unknown; notify affected customer/store safely; reconcile before cancellation; do not assume a timeout means supplier never accepted |
| Dispatch delayed | Compare promise snapshot with server time; show delay without invented dates; support cancellation eligibility per verified supplier/policy stage, not automatic reversal of dispatched units |
| Supplier partial cancellation | Lock allocations, cancel only confirmed unshipped units, cap against ordered net quantity, append proportional adjustment and release/restock once |
| Cancellation races dispatch | Lock command/allocation/item; provider confirmation wins only for still-unshipped units; otherwise move to return workflow; ambiguous provider state quarantined |
| Duplicate/out-of-order events | Same key/hash no-op; different hash quarantine; older version cannot regress delivered state; record attempts and causal event, fetch authoritative status on contradiction |
| Supplier suspended / mapping paused | Block new quotes/orders/forwarding; retain historical links and active tracking/cancellation support; no catalog rewriting or leaked supplier cost |

Only service transitions status; merchants request actions for their store, customers request their own purchased units. Parent state derives from all store/line outcomes, never from a single last webhook. Dispatch/tracking may continue for existing orders of a subsequently suspended store, with revocation and support escalation rules.

## 8. Partial cancellation, return and refund accounting

- Allocate immutable line discounts, taxes and store shipping in minor units at order creation using deterministic largest-remainder allocation and stable line-ID tie-breaks. Store the policy/version and original totals; future refunds do not recompute against current prices/tax rates.
- Lock purchased line, allocations, open requests and adjustments. Net cancelled quantities + received approved return quantities cannot exceed purchased quantity; simultaneous requests cannot reserve the same units. Returns require shipped/delivered eligibility and actual received/inspected units; cancellation cannot include already shipped units.
- Examples for tests: three units at 1,000 each, discount 101 and tax 203 yields net merchandise 2,899 and tax 203; split allocations must sum to those exact values. Cancelling one unit then returning two cannot exceed the original 3,102 line total (shipping handled separately), irrespective of rounding/order of operations.
- Each accepted request appends an adjustment; gross merchandise, associated discount reversal, tax credit and shipping credit are separate components. Cancellation/return approval establishes a liability, **not** proof of a cash refund. A `refund_reserved` entry reserves refundable balance, verified future provider result appends `refund_confirmed` or `refund_failed`; failures release pending cash reservation without deleting the liability.
- Maximum new refundable cash = verified collected amount − confirmed refunds − pending refund reservations − prior dispute/chargeback recoveries attributable to the same units/amounts. No verified collection means no executable cash refund. Payment/dispute adapter and this allocation evidence must receive separate approval before any financial execution.
- Partial shipping credit follows the policy snapshot; do not refund full shipping twice across partial returns. Tax reversals use original allocation and reviewed tax policy. Supplier recovery is a separate obligation; do not treat a supplier credit as customer refund confirmation or charge the customer twice.
- Reversals append linked compensating entries, never mutate original amounts. Unique event keys and one reversal per original prevent double posting. Parent/store summaries derive from immutable adjustments and must reconcile; merchant summaries exclude other stores and private financial provider references.
- Returns, cancellation fees, refund timing/currency, shipping tax/refundability, chargeback handling and retention periods require business/legal decisions before release. No Stripe charge/transfer/payout fields are added to existing financial tables; no seller balances released.

## 9. Migration plan — only after separate execution authorization

1. **Authorization/environment gate:** obtain explicit target-backend permission, confirm physically isolated test auth/database/storage and deployment configuration, inventory hosted tables/policies/functions/permissions against repository, verify rollback/backup availability and authorization. Halt on drift. No migrations in the shared live backend as a side effect of a draft acceptance.
2. **Complete review SQL outside migrations/application:** convert this dictionary into additive candidate SQL in a review directory; enumerate each trigger/procedure signature and grants, explain security-definer roots and cost/PII retention. No generated migration journal edits, no executing candidates. This revision supplies the design, not release-ready executable SQL.
3. **Account cart batch:** create carts/items/imports with constraints/indexes, ownership-validated RPCs and RLS. Account UI/import bridge remains disabled until isolated merge tests pass. Preserve current guest cart as fallback; no import/backfill of Marketplace or PB Store carts.
4. **Order/accounting batch:** create parent/store/items/private-delivery details/requests/adjustments/events and read-only safe projections; all order/preparation/financial actions off. Do not synthesize paid orders or copy legacy financial history.
5. **Inventory batch:** create controls/reservations and guarded transactions; review coupled stock-edit validation/availability projection changes against existing editor/public-read behavior. Initialize controls lazily at zero only when there are no holds; no seed-on-page-load. Enable only in the isolated test deployment for concurrency tests.
6. **Supplier/logistics batch:** create supplier mappings, fulfillments/allocations, shipments/line allocations, durable commands/events. No credentials, supplier submissions, scheduled workers or production endpoints activated. Verify adapter signatures/idempotency/status/cancellation contracts separately.
7. **Validation and release review:** verify actual installed objects/grants/RLS/types, all security/concurrency/accounting tests, backups and feature-off existing-app checks. Apply through the managed migration tool only after authorization, one self-contained additive batch at a time; tools regenerate types. Inspect actual installed objects even if the tool reports success.
8. **Independent later gates:** account cart enablement; order creation/reservation enablement; supplier activation; payments/refunds; production database application; deployment. None is implied by schema approval, and none is authorized here.

Use no destructive changes, required columns without defaults on existing tables, table/column renames, financial data mutation or catalog backfill. New FKs/indexes restrict unsafe deletion of referenced catalog history once orders exist; retain archival rather than hard deletion and review merchant UI impact before enablement. Do not edit existing media/team/approval policies. Any necessary existing-object behavior change is separately itemized rather than concealed in a new-table migration.

## 10. Rollback and recovery plan

**This review:** rollback consists only of reverting review-document changes; there is no database or runtime change to undo.

**Before installation:** capture verified backup/recovery point, deployed code version, exact grants/policies/functions/indexes and migration batch hashes. Establish who can restore and how; availability of backups has not been verified here.

**Failed batch:** managed transactional migration rolls back that batch; inspect actual objects/journal before retry. Earlier successfully applied batches remain intact. Do not assume the entire multi-batch release rolled back.

**Applied additive schema, features still off:** keep new tables inert, revoke affected new callable/write permissions, disable only new endpoints/jobs. Leave schema/data in place, not DROP/TRUNCATE; annotate retired objects if abandoning. The unchanged app continues with browser-local cart/product pages. Fix-forward reviewed patches rather than destructive down migrations.

**Future enabled carts/orders:** disable new entrypoints and imports, stop issuing reservations/commands, preserve account carts and receipts, do not overwrite guest cart. Drain/reconcile leased/unknown supplier commands before pausing workers; stopping a worker cannot undo an external order. Release only verified pre-commit holds, never committed/shipped units. Retain read-only history and safe customer/support access. Reconcile adjustments against provider evidence before any compensation.

**Stock compatibility:** do not remove hold counters/stock-edit validation while holds remain. Under locks, release legitimate pending holds, verify zero held balances, then restore prior availability path with separately approved code. Catalog inventory cannot be restored blindly from an old snapshot after sales.

**Disaster recovery:** whole shared-backend restore would affect other businesses and requires independent authorization. Preferred recovery is targeted fix-forward with audit evidence, not overwriting production Marketplace/PB Store orders. No deletion of customer/merchant history to make tests pass.

## 11. Test/live isolation and review test plan
